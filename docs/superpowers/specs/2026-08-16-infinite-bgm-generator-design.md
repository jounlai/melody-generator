# 無限BGM生成器 設計書

作成日: 2026-08-16

## 1. 目的

事前データとして用意した **メロディー断片999個** と **コード進行99個** をランダムに組み合わせ、
ブラウザ上で BGM を無限に生成し続ける。

品質目標は **「涙を流すほど美しいメロディ」**。リズムの面白さではなく、
メロディーの輪郭と和声の陰りで感情を動かすことを優先する。

### 音楽的方向性

静かなピアノ中心のヒーリング系（サティ、久石譲の系統）。

- テンポ 66〜76 BPM、4/4拍子
- 音数は少なく、ロングトーンと間を重視
- ダイアトニック中心。ただし借用和音による陰りを要所で使う

### 「泣ける」を実装するための音楽的装置

コードトーンに素直に着地する「無難で綺麗な」メロディでは目標を達成できない。
以下を明示的にデータとロジックへ組み込む。

- **掛留・倚音**（4-3、9-8のサスペンション）— 一瞬の不協和とその順次解決
- **サブドミナントマイナー**（IV → iv）と **借用和音**（bVI、bVII）— 長調に落とす一滴の陰り
- **偽終止**（V → vi）— 終わると思わせて終わらせない
- **6度・オクターブの上行跳躍 → 順次下降** — ため息の形
- **クライマックス音は曲中に一度だけ** — 最高音を安売りしない
- **モチーフの再登場** — 一度聴いた旋律が形を変えて帰ってくる

## 2. 出力形式

ブラウザでのリアルタイム無限再生。HTML + 素の ESM + Web Audio API。

- ビルドツール、フレームワーク、外部パッケージをすべて使わない（依存ゼロ）
- 音源もサンプルファイルを使わず Web Audio で合成する。
  ページを開いた瞬間に鳴り、リポジトリはテキストのみで完結する
- ESM は `file://` から読めないため、`npm start` で `python3 -m http.server` を起動して開く

## 3. データモデル

### 3.1 音高表現: キーに対するスケール度数

**絶対音名では持たない。** 音名で持つと断片が特定のキー・コード専用になり、
99個の進行と自由に掛け合わせられなくなる。

度数で持つことで、**同じ断片が違うコードの上に乗るだけで別の表情になる**。
999 × 99 の組み合わせが意味を持つのはこの表現のときだけである。

`deg` は 1 起点の通しスケール度数とする（1 = キーのトニック、8 = 1オクターブ上のトニック、
15 = 2オクターブ上）。オクターブを別フィールドに分けず通し番号にすることで、
音域・跳躍幅の計算が引き算だけで済む。

#### 断片はメジャー／マイナー両対応にする

断片自体は調性を持たない。度数から半音への変換テーブルを mode によって切り替える。

- major: `0, 2, 4, 5, 7, 9, 11`
- minor（自然的短音階）: `0, 2, 3, 5, 7, 8, 10`

**同じ断片がメジャー進行の上では明るく、マイナー進行の上では切なく響く。**
断片を mode 別に作り分ける必要がなくなり、999個の実効的な多様性が2倍になる。

ただしコード適合の判定結果は mode によって変わるため、`fitChords` だけは
mode ごとに分けて保持する（3.2 参照）。

### 3.2 メロディー断片: 2小節を1単位

1小節では輪郭（起伏）が作れず、4小節では接続点が少なく組み合わせの妙が出ない。
2小節は人の呼吸1回分にあたり、テンポ66なら約7秒。

```json
{
  "id": "m0421",
  "notes": [
    { "deg": 5, "beat": 0.0, "dur": 1.5, "vel": 0.72 },
    { "deg": 6, "beat": 1.5, "dur": 0.5, "vel": 0.65 }
  ],
  "startDeg": 5,
  "endDeg": 3,
  "contour": "arch",
  "range": [3, 10],
  "peakDeg": 10,
  "peakBeat": 4.5,
  "tension": 3,
  "density": 0.6,
  "tags": ["suspension-4-3", "leap6-up-then-down"],
  "fitChords": {
    "major": ["I", "vi", "IVM7"],
    "minor": ["i", "VI", "iv"]
  },
  "score": 87.4
}
```

- `beat` は2小節通しの拍位置（0.0 〜 8.0）、`dur` は拍数、`vel` は 0.0〜1.0
- `contour`: `arch` / `descend` / `ascend` / `wave` / `question` / `answer`
- `tension`: 1〜5
- `density`: 音符の詰まり具合 0.0〜1.0

メタデータは飾りではなく、**組み立て時の3フィルタが読む値そのもの**である。
`startDeg`/`endDeg` が接続判定、`tension`/`peakDeg` が起伏カーブ判定、
`fitChords` がコード適合判定に使われる。

### 3.3 コード進行: 4小節を1単位、99個

```json
{
  "id": "p07",
  "mode": "major",
  "bars": [
    { "chord": "I" },
    { "chord": "V/3" },
    { "chord": "vi" },
    { "chord": "iv" }
  ],
  "cadence": "deceptive",
  "tension": [1, 2, 3, 4]
}
```

断片が2小節、進行が4小節なので **1進行 = 断片2個** できれいに噛み合う。

99個は無作為に作らず、**泣ける進行の定石カタログ（約20種）を土台に、
転回形・代理コード・テンション付加・部分転調の変形ルールで99個へ展開する**。

カタログに必ず含めるもの:

- **カノン進行系** — `I - V/3 - vi - I/5 - IV - I/3 - IV - V`（ベースが順次下降する）
- **サブドミナントマイナー** — `IV - iv - I`
- **偽終止** — `V - vi`
- **借用和音** — `bVI`、`bVII`
- **王道進行** — `IV - V - iii - vi`

内訳の目安はメジャー系 約55個、マイナー系 約44個。

### 3.4 格納形式

`src/data/melodies.json`（999件）と `src/data/progressions.json`（99件）。
生成スクリプトが一度走って書き出し、以降ランタイムはこれを読むだけ。
ルールを直したくなれば再生成で丸ごと入れ替わる。

## 4. 事前データの生成

### 4.1 断片の候補生成（3段階）

ランダムに音を置いて選抜するのは効率が悪いため、筋の通った候補を数万個作ってから絞る。

1. **輪郭テンプレートを引く** — アーチ型 / 下降型 / 上昇型 / 波型 /
   問いかけ型（宙に浮いて終わる） / 応答型（着地する）
2. **リズム型を引く** — 8分音符以下は控えめ。付点4分＋8分、2分音符＋4分、
   シンコペーション少々
3. **輪郭とリズムに沿って度数を埋める** — このとき掛留・倚音を意図的に混ぜる

### 4.2 美しさスコア（減点と加点の両輪）

減点法のみでは「無難で泣けない」ものが上位に来る。加点法を必ず併用する。

**減点（安全性）**

- 3度以上の跳躍が連続する
- 跳躍後に同方向へさらに跳躍する
- 同じ音を過度に連打する
- 音域が12度を超える
- 強拍の非和声音が解決しない
- 音符が細かすぎる（ヒーリング系として）

**加点（情動）**

- 掛留・倚音があり順次下降で解決する
- 6度／オクターブの上行跳躍 → 順次下降（ため息の形）
- 前半1小節のリズム型を後半が反復する（内部モチーフ）
- ロングトーンで終わる（余韻）
- 最高音が断片中1回だけ

### 4.3 選抜は層化抽出で行う

**単純なスコア上位999件を採用してはならない。** それをやると似た優等生ばかりが並び、
無限に聴いたとき必ず飽きる。また、組み立て側のフィルタが候補切れを起こしやすくなる。

`輪郭タイプ × 緊張度(1-5) × 終止度数` のバケットごとに定員を設けた層化抽出とし、
「静かで問いかけて終わる断片」も「クライマックス用に高く張った断片」も
必ず一定数確保する。

### 4.4 メタデータの算出

採用が決まった断片について、以下を生成時に計算して JSON へ焼き込む。
ランタイムでの再計算は行わない（フィルタは999件を毎曲走査するため、事前計算が効く）。

- `startDeg` / `endDeg` / `range` / `peakDeg` / `peakBeat` / `density` — 音符列から機械的に算出
- `contour` — 音高列の形状を輪郭テンプレートに照合して決定
- `tension` — 音域の高さ、非和声音の割合、跳躍量から 1〜5 に量子化
- `tags` — 掛留・倚音・跳躍パターンの検出結果
- `fitChords` — **メジャー／マイナー双方について**、全ダイアトニックコードと
  主要な借用和音（iv、bVI、bVII など）を総当たりで適合判定し、
  通ったコードを列挙する

## 5. 曲の組み立て（ランタイム）

### 5.1 曲の構造

**A(8小節) - A'(8) - B(8) - A''(8) = 32小節**。テンポ66で約2分。

8小節セクション = 4小節進行 × 2周 = 断片4個。曲全体で断片16スロットを埋める。

**コード進行は曲ごとに2つだけ引く。**

- `P1` — A / A' / A'' で使う（A系セクションの土台）
- `P2` — B で使う（B は別の景色にする）

`P1` と `P2` は同じ `mode` の中から引く。曲の途中で長調と短調が入れ替わると、
2分の曲としては散漫になるため。

`A'` と `A''` は `P1` をそのまま繰り返すのではなく、**`P1` の変形**を使う。
変形は以下のいずれかを適用する。

- 転回形の差し替え（`V` → `V/3` など。ベースラインの動きが変わる）
- 終止コードの代理コード化（`I` → `vi`、`IV` → `iv` など）
- テンションの付加（`IV` → `IVM7`）

進行を2つに絞ることには実務上の理由もある。**モチーフを再登場させる断片が、
再登場先のコードにも適合することがほぼ保証される**（5.2）。

緊張度カーブ:

```
A    A'   B          A''
低 → 中 → 最高(山) → 解決して静かに
                ↑
        最高音はここに一度だけ
```

**クライマックス音を曲中1回だけにする**実装: A / A' / A'' では断片の `peakDeg` に
上限を課し、B の特定位置でだけその上限を外す。

### 5.2 モチーフの再登場

**A で選んだ断片IDを記録し、A' / A'' で同じ断片を変形した進行の上に再登場させる。**

「さっき聴いた旋律が形を変えて帰ってきた」という感覚を生む。
類似度検索は行わず、IDを保持するだけで実現する。

再利用するスロットを明示する。A の4断片を `f1 f2 f3 f4` とすると:

| セクション | スロット1 | スロット2 | スロット3 | スロット4 |
|---|---|---|---|---|
| A   | f1（新規） | f2（新規） | f3（新規） | f4（新規） |
| A'  | **f1 再利用** | 新規 | 新規 | 新規 |
| B   | 新規 | 新規 | 新規（クライマックス） | 新規 |
| A'' | **f1 再利用** | 新規 | **f4 再利用** | 新規（終止を強化） |

冒頭の `f1` が3回帰ってくることで曲の顔が立ち、`f4` の再登場が着地感を作る。
16スロット中3つだけの再利用なので、単調にはならない。

**再利用時のフィルタ扱い**: 再利用される断片は接続フィルタと起伏カーブフィルタを免除する
（すでに決まった断片なので選び直しは発生しない）。ただし移動先のコードに対して
コード適合だけは検査し、万一不適合なら **同じ `contour` と同じ `startDeg` を持つ別の断片**で
代替する。5.1 で進行を `P1` の変形に限定しているため、この代替はほとんど発動しない。

### 5.3 断片選択の3フィルタ

999個を以下の3フィルタに通し、**通った候補の中からランダムに引く**。

1. **コード適合** — 強拍の音が今のコードのコードトーン、または解決する非和声音であること
2. **接続の滑らかさ** — 前断片の `endDeg` と次の `startDeg` の差が2度以内。
   ただしセクション頭では跳躍を許可し、クライマックス直前では6度上行跳躍を優先する
3. **起伏カーブ適合** — 現在のセクションが要求する `tension` と音域上限に収まること

### 5.4 フォールバック（必須）

候補0件は確実に起きる。フィルタを 3 → 2 → 1 の順に緩め、
それでも0件なら **「今のコードのコードトーンをロングトーンで1つ鳴らす」** を最終手段とする。

無音や例外で音楽が止まることは、どんな品質低下よりも避ける。

### 5.5 決定論性とシード

曲は **シード値と作曲パラメータの組**から完全に決定論的に生成される
（`mulberry32` によるシード付きPRNG）。同じシード＋同じ作曲パラメータは必ず同じ曲を生む。

`Math.random()` の使用は **`synth.js` のリバーブ用インパルス応答生成と
パッドのデチューンに限る**。作曲経路（`compose.js`）と演奏の揺らぎ（`player.js`）は
すべてシード由来のPRNGを使う。演奏の揺らぎには曲のシードから派生させた
別系列のPRNGを用い、作曲側の乱数列を汚さない。

再現の単位がシード単体ではなく組になるため、UI では両者をまとめた「曲コード」を
提示する（8.5 参照）。

## 6. サウンド

### 6.1 3レイヤー構成

| レイヤー | 中身 | 役割 |
|---|---|---|
| メロディー | 基音＋2/3/4倍音の加算合成。倍音ほど速く減衰。わずかなデチューンと微量のアタックノイズ | 主役。最前面 |
| 伴奏 | 同じ音源の高倍音を削ったもの。ロングトーンとゆるいアルペジオ | 下支え。-8dB 程度 |
| パッド | 三角波＋ローパス、2〜3秒かけて立ち上がる和音の持続音 | 空間を埋める。無いと合成ピアノは寒々しい |

全体を **ConvolverNode のリバーブ**に通す。インパルス応答はノイズ×指数減衰で
手続き生成した3.5秒程度のもの。ヒーリング系はリバーブが音色の半分を作る。
最後にソフトリミッタ（DynamicsCompressorNode）で音割れを防ぐ。

### 6.2 揺らぎ

完全にクオンタイズされた演奏は、メロディーが良くても冷たく聴こえる。

- 各音の発音時刻に **±10ms** のランダムずれ
- ベロシティに **±8%** のばらつき
- **フレーズの頂点音をわずかに遅らせ、少し長めに鳴らす**（テヌート。効果が最も大きい）
- **フレーズ末で軽くリタルダンド**
- コードが変わるまで音のリリースを長く引く（サステインペダル相当）

### 6.3 再生スケジューラ

`setTimeout` 直打ちでは精度が足りずヨレる。**先読みスケジューラ**を使う。

100ms間隔のタイマーで「250ms先まで」の音を `audioContext.currentTime` 基準で予約する。
タイマーが多少遅れても音は正確な時刻に鳴る。

曲が終わったら **3〜4秒の余韻**（リバーブの尾を残したまま）を置いて次の曲へ移る。

### 6.4 調整方針

サウンドのパラメータ（音量バランス、リバーブ量、音色の明るさ）は
実装後に実際に聴いて調整する。設計時点では確定させない。

**そのため、これらの値はコードに直接書かず、すべて画面のコントロールから
変更できるようにする**（8.2 参照）。`synth.js` は設定オブジェクトを引数で受け取り、
サウンド系の変更はゲイン値の書き換えだけで即座に反映する。

## 8. UI

### 8.1 基本操作

- 再生 / 停止
- 次の曲へスキップ
- **現在の曲コードの表示とコピー**
- 曲コードの入力欄（貼り付けて同じ曲を再生）

### 8.2 後から調整したい値はすべて画面から変えられるようにする

音楽の良し悪しは耳で聴かないと決められない。コードを開いて数値を書き換えて
リロードする、という往復が発生した時点で調整は続かなくなる。
**「後から調整しうる値」はハードコードせず、すべて画面のコントロールに出す。**

これを支えるための構造上の決まりごと:

- 調整可能パラメータは **`src/settings.js` の1箇所**に定義を集約する。
  各項目は「キー / 表示名 / 型 / 範囲 / 既定値 / 反映タイミング」を持つ
- `compose.js` / `synth.js` / `player.js` は設定値をハードコードせず、
  **必ず設定オブジェクトを引数で受け取る**
- UIパネルは `settings.js` の定義から**自動生成する**。
  パラメータを1つ増やすときに触るファイルは `settings.js` だけで済む
- 値は `localStorage` に保存し、次回起動時に復元する
- 「既定値に戻す」ボタンを置く

### 8.3 調整項目

**サウンド（変更が即座に反映される）**

| 項目 | 範囲 | 既定値 |
|---|---|---|
| 全体音量 | 0〜100% | 70% |
| メロディー音量 | 0〜100% | 100% |
| 伴奏音量 | 0〜100% | 45% |
| パッド音量 | 0〜100% | 35% |
| リバーブ量 | 0〜100% | 45% |
| 音色の明るさ（倍音量） | 0〜100% | 50% |

**演奏の揺らぎ（次の曲から反映）**

| 項目 | 範囲 | 既定値 |
|---|---|---|
| タイミングの揺らぎ | 0〜30ms | 10ms |
| ベロシティの揺らぎ | 0〜25% | 8% |
| 頂点音のテヌート | ON / OFF | ON |
| 終盤のリタルダンド | ON / OFF | ON |

**作曲（次の曲から反映）**

| 項目 | 範囲 | 既定値 |
|---|---|---|
| テンポ | 52〜92 BPM の範囲指定 | 64〜76 |
| キー | ランダム / 12音から指定 | ランダム |
| 長調の比率 | 0〜100% | 55% |
| 曲の長さ | 16 / 32 / 64 小節 | 32小節 |
| 起伏カーブの強さ | 0〜100% | 100% |
| 接続の跳躍許容度 | 2〜6度 | 2度 |
| モチーフ再登場 | ON / OFF | ON |
| 曲間の余韻 | 0〜10秒 | 3.5秒 |

### 8.4 反映タイミングの扱い

サウンド系はゲイン値を書き換えるだけなので即座に反映する。

作曲系と揺らぎ系は、現在の曲がすでに組み上がっているため**次の曲から反映**する。
変更時に「次の曲から反映されます」と表示し、隣に **「今すぐ作り直す」** ボタンを置いて、
待たずに聴き比べられるようにする。

### 8.5 曲コードは設定込みで再現する

作曲パラメータを変えると、同じシードでも違う曲になる。そのため再現の単位は
シード単体ではなく **「シード＋作曲パラメータ」** とする。

これを URL ハッシュ（例: `#s=a3f91c&t=64-76&len=32&maj=55`）で表現し、
画面には「曲コード」としてコピー可能な形で表示する。
ハッシュ付きURLを開くとその設定とシードで再生が始まる。
サウンド系パラメータは曲の内容に影響しないためハッシュに含めない。

この仕組みが「今のすごく良かった」を取り逃さないための保存機能にあたる。

## 9. テスト

`node:test` を使う（追加依存なし）。耳以外で判定できる部分のみをテストする。

- **theory** — 度数→MIDI番号の変換、コードトーン判定
- **score** — 意図的に作った「良い断片」が「悪い断片」より高得点になること
- **data** — 999件 / 99件が揃っていること、全件がスキーマに適合すること、
  層化バケットに偏りや空きがないこと
- **compose** — 同じシード＋同じ作曲パラメータが同じ曲を生むこと（決定論性）、
  生成された曲が制約を満たすこと（接続の跳躍幅、クライマックスが1回だけ、コード適合率）、
  フォールバック発動時も無音の小節を作らないこと
- **settings** — 全パラメータが範囲と既定値を持つこと、
  範囲外の値が既定値に丸められること、
  曲コード（URLハッシュ）の書き出しと読み込みが往復すること、
  **作曲パラメータを変えると曲が実際に変わること**（設定が握り潰されていないことの検査）

`synth.js` と `player.js` の音響部分はテストしない。Web Audio は Node で動かず、
音の良し悪しは耳でしか判断できないため。実装後に実際に聴いて調整する。
ただし `player.js` のうち**イベント列の組み立て（揺らぎの適用を含む）は
純関数として切り出してテストする**。

## 10. 実装順序

1. `rng.js`、`theory.js`、`settings.js` — 土台
2. `tools/` 一式 — 事前データ生成（`progressions.json` → `melodies.json` の順）
3. `compose.js` — 曲の組み立て
4. `synth.js`、`player.js` — 音源と再生
5. `index.html`、`ui.js`、`main.js` — UI と設定パネル

`settings.js` を最初に置くのは、後続の全モジュールが設定オブジェクトを
引数で受け取る前提で書かれる必要があるため。後から差し込むと全モジュールの
書き換えになる。

音が出るのは最後だが、その前に「生成された曲が制約を満たしている」ことは
テストで確認できる。

## 11. スコープ外

- MIDI / WAV の書き出し
- サンプルベースの音源
- ユーザーによるメロディー編集機能（断片を直接書き換えるエディタ）
- 曲の音声ファイルとしての保存（曲コードによる再現で代替する）
- お気に入りの一覧管理（曲コードのコピーで代替する）
